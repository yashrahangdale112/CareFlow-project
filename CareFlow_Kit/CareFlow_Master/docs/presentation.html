SLIDE 3 — Problem statement

TitleThe Problem: pathways are designed one way, executed another
Bullets • A patient journey runs Registration → Triage → Tests → Diagnosis → Treatment → Discharge
• In reality every journey differs: repeated tests, ICU escalation, delayed discharge
• Traditional dashboards show aggregates — bed occupancy, average stay, monthly cost
• Aggregates reveal that something is slow, never where inside the process
• Result: waiting time and cost accumulate invisibly, and nobody owns the bottleneck
Bolne ke liye: “Ek line me problem — hospital ko pata hota hai ki patient zyada der ruk raha hai, lekin yeh nahi pata ki process ke andar exactly kahan ruk raha hai.”

SLIDE 4 — What is process mining

TitleSolution Approach: Process Mining on the Event Log
Bullets • An event log records every activity: case_id + activity + timestamp
• Discovery — derive the real process model from data, no interviews needed
• Conformance — measure how far reality deviates from the expected pathway
• Enhancement / prediction — quantify bottlenecks and forecast outcomes
• Implemented in Python with pandas, networkx, scikit-learn, Streamlit; pm4py adds the official miner algorithms

SLIDE 5 — Data

TitleDataset: 6 months of hospital activity
Bullets • 1,500 patient cases · 13,664 raw events → 13,583 after cleaning
• 15 clinical activities · 28 resources · 10 departments
• Window: 01 Mar 2026 → 31 Aug 2026
• Required columns: case_id, activity, timestamp (+ optional resource, cost, durations)
• Cleaning: 81 duplicate events removed, 203 blank resource fields filled
• Four clinical pathway templates: Outpatient 35 %, Emergency Surgical 25 %, Chronic Follow-up 25 %, ICU Escalation 15 %

SLIDE 11 — Conformance and prediction

TitleConformance Checking and Long-Stay Prediction
Bullets Conformance (token-based replay):
• Model = 28 DFG edges (occurrence ≥ 3)
• Average fitness 1.0000 · 100 % cases conforming
• Explanation: synthetic data is generated from fixed templates, so the model can replay its own data perfectly; on a real hospital log expect 0.70–0.95

Prediction:
• Target: length of stay > 24 hours (1.13 % positive rate)
• Three algorithms × two feature sets (full 19 vs leakage-free 14)
• Production model: Gradient Boosting — accuracy 0.997 · precision 1.000 · recall 0.667 · F1 0.800 · ROC-AUC 0.998
• Zero false alarms on the test set
• Top drivers: number of events, unique activities, ICU transfer, rework count

SLIDE 13 — Recommendations, limitations and conclusion

TitleRecommendations, Limitations and Next Steps
Bullets Recommendations
• Decongest Observation — second ward-round slot plus a dedicated discharge desk
• Fast-track morning laboratory sampling (second-largest wait category)
• Roster to the load curve: Friday ~14:00, late-morning to mid-afternoon band
• Deploy the leakage-free long-stay flag at admission (zero false positives)
• Standardise the top 5 variants, then re-run conformance quarterly

Limitations
• Synthetic reference data; conformance 1.0 is a property of the generator
• Only 3 positive test cases — wide confidence interval on F1 and recall
• DFG replay is less precise than Petri-net alignment

Next steps
• Integrate a real HIS/EMR feed (HL7 / FHIR), add class balancing and SHAP explanation,
build a what-if simulator, add drift monitoring

Conclusion: from raw event log to actionable, deployable insight — in one reproducible pipeline.
